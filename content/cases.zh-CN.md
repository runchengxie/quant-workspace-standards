# 四次事故，四项值得保留的检查

运行经历来自分享初稿，仓库记录于 2026 年 10 月 12 日核对。五个 PR 所在仓库已确认公开。下面的证据说明区分记录支持的事实和个人回忆。删除行数不能直接当作重复代码行数。

## 长假超过了七天的新鲜度窗口

周报在长假后被拦住。修复按上一个有效交易日验证数据新鲜度，并核对交易日历证据，避免只按自然日间隔判断。

工程上需要明确时间口径，并在生产消费边界测试连续休市。

<details><summary>证据与范围</summary>

[信息平台 PR #216](https://github.com/runchengxie/quant-intel-platform/pull/216)，合并 `4131c7e`，实现 `21f457b`，包含 performance 校验、回归测试及新鲜度契约。PR 确认八个自然日遇到七天规则。provider 证据为可选项，没有证据的产物仍使用七个自然日规则，证据格式或内容不合法时拒绝通过。

</details>

## 消息可能发成功了，确认却没回来

通知链路需要防止重复发送。PR #220 保留发送结果未知的状态，阻止不确定发送后的 fallback，将发送身份绑定到内容，并验证业务恢复。把未知当作失败重试，就可能重复发消息。

工程上需要表示未知状态，明确重试边界，并检查恢复后业务是否真的正常。

<details><summary>证据与范围</summary>

[信息平台 PR #220](https://github.com/runchengxie/quant-intel-platform/pull/220)，提交 `0aa2bdf`，涉及发送状态、意图、sender 和回归验证。早上 9 点调整为 7 点、约两周才稳定等细节来自个人回忆，不能单靠此 PR 证明。这些修复也不等于所有传输故障下都能保证消息恰好发送一次。

</details>

## 两个仓库保留了重叠的前端职责

信息平台退役报告前端，Pages 将新鲜度监控交给 Deploy。明确谁生成、谁展示、谁部署和谁监控，有助于找到实际生效的修改位置。

工程上需要给能力明确归属，并测试公开边界。

<details><summary>证据与统计口径</summary>

[信息平台 PR #211](https://github.com/runchengxie/quant-intel-platform/pull/211)，合并 `4859b20`，实现 `f253443`，改动 201 个文件，新增 234 行，删除 36,342 行。退役 diff 包含源码、测试、配置和生成产物，不能称为测量得到的重复源码行数。[详情页 PR #98](https://github.com/runchengxie/quant-intel-pages/pull/98)，提交 `10a536c`，将新鲜度监控交给 Deploy。报告出现不同版本和 AI 写错仓库来自个人叙述，记录不能证明模型的动机。

</details>

## 检查工具也要检查自己的范围

质量扫描器有针对多层 Git 目录及目录边界的回归测试。检查通过的前提，是它确实检查了目标文件。

工程上需要把扫描范围和违规数量分别验证。

<details><summary>证据与样本范围</summary>

[质量工具 PR #10](https://github.com/runchengxie/quant-code-quality/pull/10) 是初稿提供的来源。当前本地 `tests/test_scanner.py` 覆盖多层 Git 目录。PR 记录了对 quant-research 配置范围的只读审计，旧扫描器发现 674 个文件、12 个长函数，修复后发现 1,656 个文件、94 个长函数。这是文件发现和维护性统计，不是测试覆盖率。扫描范围变小也不能证明 AI 有意隐藏错误。

</details>
