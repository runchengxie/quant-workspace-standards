# Code 工作区规范

本目录包含多个相互独立的仓库。修改前先识别目标仓库并阅读该仓库自己的 `AGENTS.md`，不要把相邻仓库视为同一个项目。

> 本文件是 `AGENTS.md` 的简体中文参考译文。英文版本是权威规范；两者有差异时以英文版本为准。

## 语言与国际化

- 工作区规范、技术要求和仓库开发文档以英文为权威语言。中文译文仅作辅助参考；两种语言内容不一致时，以英文版本为准。
- 根目录的 `AGENTS.md` 是规范的英文主版本，`docs/standards.zh-CN.md` 是简体中文参考译文。修改规范时应在同一变更中同步更新两份文件，且不要只在译文中增加要求。译文应明确标注为参考材料，不要将它作为另一份 agent 指令文件。
- 支持多语言的用户界面应将可翻译文本放在语言资源文件中，而不是写死在 UI 组件内。使用稳定且表达语义的键、动态文本插值、支持复数规则的消息，以及符合语言习惯的格式化方式。
- 默认使用英文；产品支持多种语言时，应提供明确的语言切换入口。条件允许时记住用户选择；缺少译文时回退到英文。
- 语言选择应与业务逻辑分离。时间戳和其他值按数据契约存储；展示时根据所选语言和明确指定的时区进行格式化。
- 机器日志、API、持久化数据和内部标识应保持稳定且不依赖语言。翻译面向用户的界面和文档，不要因语言设置改变数据或协议值。

## 默认开发流程

1. 首先只读检查目标仓库的工作树、分支、远端和已有工作树，保留其他 agent 的改动。
2. 拉取远端状态。默认以用户自己的仓库或 fork 为目标，从其中的 `main` 创建任务分支和独立工作树。每个任务、每个 agent 使用独立的工作树和分支。
3. 临时工作树统一放在 `$CODE_ROOT/.worktrees/<repo>-<topic>`。代码、测试和文档都在任务工作树中修改，不要直接在共享的 main 检出目录里开发。
4. 在任务工作树中完成所需验证并提交。默认将任务分支推送到用户自己的仓库或 fork，并创建以该仓库 `main` 为目标的 PR。除非用户明确要求，不要向原作者或上游仓库开 PR。确认仓库归属和实际远端名称，不要假设目标远端一定是 `origin`。
5. PR 评审、必需检查和冲突处理完成后再合并。不要绕过 hooks、直接推送到 `main` 或通过强推争抢合并。
6. 确认 PR 已合并且任务工作树中没有唯一且未保存的内容后，只删除本任务创建的远端分支、移除本任务的工作树并删除本地任务分支。不要删除仍处于检出状态的分支。
7. 仅当主检出干净时才快进同步 `main`。交付时说明 PR、合并 SHA、实际验证结果和遗留事项。

## 安全边界

- 只清理本任务创建的分支和工作树。不要因为其他内容看起来过期就删除它们。
- 不要使用 `--force`、`reset --hard` 或覆盖文件来丢弃未保存改动。若归属不明、发生冲突或必需检查失败，应报告并保留可恢复状态。
- 跨仓库改动应在各自仓库开 PR，并先合并 provider，再合并 consumer。不要让生产依赖未合并的开发路径。
- 仓库 hooks 是共享配置。不要在任务工作树里重新安装或改写 hooks。
- 原始数据、运行结果和凭证应放在仓库外。定时任务使用稳定的生产发布路径，不要引用临时工作树。
- 访问 GitHub 时先使用 GitHub CLI 已配置的凭证，并在远端写操作前验证认证状态。认证失败时遵循仓库的凭证说明。不要打印、提交或把访问令牌持久化到 shell 配置或仓库中。
- 用户级文件和本地工作区配置不属于 Git 仓库，不能通过 PR 提交。用户提出修改时应直接在原处修改；不要为了版本化它们而初始化或重构整个 `code` 目录。

## 项目配置与凭证

- 对于 `~/code/` 下的项目，将个人项目配置、生产设置、凭证和机器专属路径放在仓库和临时工作树之外的私有 owner 命名空间中，例如 `~/.config/<owner>/`。
- 创建配置文件前，先检查并沿用 `~/.config/<owner>/projects/`、`deployments/` 和 `shared/` 下已有的分组。避免在 `~/.config/` 顶层与 owner 命名空间中同时保存同一份凭证。
- 项目个人设置放在 `projects/`；部署专属设置放在 `deployments/<repo>/`；只有真正由多个项目共享的配置才放在 `shared/`。优先使用基于 `XDG_CONFIG_HOME` 或 `$HOME` 的路径；可分享代码中不要写死个人绝对路径。
- 凭证文件权限设为 `0600`，仅存放凭证的目录权限设为 `0700`。日志、运行结果和原始数据应放在各自指定的位置，而不是配置目录中。
- 将工作区开发规范保存在有效 Git 仓库中，并根据内容选择合适的访问级别。公开仓库只放通用规范；移除个人主机名、绝对路径和机器专属凭证路径。工具专属设置应放在相应工具要求的位置。

## 数据与生成文件

- 默认将项目数据、保留的运行状态、报告、模型、图表和其他生成文件放在 `~/data/` 下。不要把它们放进源码仓库、临时工作树或私有 owner 配置命名空间。
- 将 `~/code/` 下的项目分组映射到 `~/data/`。例如，`~/code/quant/<repo>/...` 对应的数据应放在 `~/data/quant/<repo>/...`。条件允许时保留项目内的相对目录结构，便于关联源码和生成物。
- 多个仓库共享的数据应放在权威 owner 的项目目录中。消费者通过明确的路径或已发布的数据资产契约访问，不要仅为镜像源码目录而复制数据。
- 仓库自己的 `AGENTS.md`、数据契约或生产配置可以指定稳定的数据根目录、外部存储、发布目录或其他布局。遵守更具体的要求。
- 修改现有数据目录前，先盘点符号链接、清单、`current`/`latest` 别名、运行中的任务和下游引用。目录映射约定不代表可以移动或删除现有数据。

各仓库自己的 `AGENTS.md` 保留更具体的质量门禁、权限和生产边界要求。
